# Changelog

本文件记录 0.3.0-alpha 的变更。格式遵循 [Keep a Changelog](https://keepachangelog.com/zh-CN/1.1.0/)。

## [0.3.0-alpha] - 2026-08-20

对应提案 `20260818-migrate-phase1-engine-completion`（架构收敛 M1：引擎补全）。

0.2.0-alpha 让失败可见，本版本让**配置真的被消费**。在此之前，`method`、`extra_files`、
`remove_scripts`、`image`、`files` 这些字段全是零消费者：写在配置里、出现在文档里、
从不影响任何行为。引擎实际只有一条路径 —— 下载完跑脚本。

因此本版本的主题是把"字段"变成"能力"，代价是几处刻意的破坏性变更：
凡是过去靠"字段被忽略"才碰巧能跑的配置，现在会立刻报错或换一种方式生效。

### ⚠️ BREAKING CHANGES

- **`method` 从被忽略改为按语义分发。**
  六种取值各有实现：`script`（跑脚本，等价于旧行为）、`binary`（解压 + 放置可执行文件 + chmod）、
  `package`（交给目标机的包管理器）、`container`（拉镜像 + 生成包装脚本）、`source`（拉源码编译）、
  `manifest`（明确报"尚未实现"，它是路线图上的合法取值，与拼错的取值分开报错）。
  *影响*：过去写了 `method: binary` 的资源，其真正的动作往往手写在自己的 `post_install` 里；
  分发一旦生效，`binary` 会导致二次安装，`package` 会去装一个并不存在的同名包。
  *迁移*：依赖旧行为（一切都只是跑脚本）的资源显式写 `method: script`。
  仓库内 `pkg/cluster/kubernetes.go` 的六处已按此适配。
  *回滚*：`git revert` 对应提交，字段回到零消费状态。

- **删除顶层 `proxy:` 配置键，`download` 改与 `install` 同读 `github_proxy`。**
  此前两条路径读的不是同一个键：同一份配置，`somcli install` 认代理、`somcli download` 不认。
  *影响*：配置里写了 `proxy:` 的会因严格解析直接报"未知字段"——报错比装错好。
  *迁移*：把 `proxy: X` 改成 `github_proxy: X`。

- **已记账的资源默认被跳过。**
  新增 `<workdir>/state.json` 记录"哪个节点装了什么版本"，并**参与执行决策**：
  按 `name@version` 命中则跳过（按 `name` 判断的话升级永远装不上）。
  *影响*：同一份配置第二次执行不再重复安装 —— 这是行为变化，不是优化。
  *迁移*：要强制重装用 `--force`（它同时越过状态记录与 `check` 探针），
  或者改 `version:`。删掉 `state.json` 等于回到无状态执行。

- **`images` 子命令的失败路径退出码由 0 变为非 0。**
  `pull` / `push` / `import` / `export` 此前对每张失败的镜像只打一行警告然后返回成功：
  一张都没拉到也照样 exit 0。现在逐张收集失败、整批以非 0 退出并列出失败的镜像；
  且**有失败就不写镜像清单**（清单是"这些镜像已在本地"的凭据，下游 `export`/`push` 照着它干活）。
  *影响*：把 `somcli images` 包在离线打包脚本或 CI 里的调用方，此前拿到的一直是 0。
  *迁移*：检查调用方是否依赖"镜像操作永远成功"这一（错误的）假设。

- **compose 缓存目录名修正：`docker-comopose` → `docker-compose`。**
  *影响*：旧缓存目录失效，下次安装会重新下载一次。属可接受的一次性损失。

### Added

- `somcli uninstall -f <file>`：按声明的逆序执行 `remove_scripts`。
  入口与 `install` 共用 `-f`/`-n` 标志与错误措辞。此前 `remove_scripts` 是零消费者，
  配置里写了卸载动作却没有任何命令会执行它。
- `somcli status`：读 `state.json`，列出已记账的资源与节点（不声明 `hosts` 的显示 `(local)`）。
- `--force`：越过状态记录**与** `check` 探针。只挂在 `install` 上。
- `--parallel N`：节点级并发。每条脚本是一道栅栏（所有节点跑完第 *i* 条才开始第 *i+1* 条），
  结果按声明顺序收集与打印，因此"并发的结果与串行一致"是可断言的。`N <= 1` 走原串行路径。
- 资源级 `check:`：探针**退出 0** 即跳过整个资源（`pre_install` 也不跑）。
  惯用写法是 `command -v jq` / `test -f ...` / `systemctl is-active ...` —— 成功表示东西已经在了。
  探针失败不是错误，就是"还没装"。
- 资源级 `on_error: abort|continue`：作用域限于脚本阶段（`pre_install` / method /
  `post_install` / `remove_scripts`）。下载、文件分发的失败一律致命 ——
  目标机上没有产物却继续往下跑，后面的报错全是派生的。
  `continue` 之后**仍以非 0 退出**并在末尾聚合列出失败的资源与节点。
- 配置级 `vars:` 与 `--set k=v`：自定义变量走 `{{.Vars.xxx}}` 命名空间，
  不平铺到顶层（平铺则用户一个 `vars: {WorkDir: ...}` 就能遮掉内置变量，
  而遮掉之后的症状是产物落到别处，很难查）。
- 资源级 `install_dir`（缺省 `/usr/local/bin`）、`build:`（`method: source` 的构建命令，
  缺了直接报错，不去猜 `./configure` / `make` / `cargo`）、`files:`（`method: binary`
  时指定归档内要装哪几个可执行文件，留空则装所有带可执行位的）。
- 模板变量 `{{.UnameArch}}`：`uname -m` 风格的架构名（`x86_64` / `aarch64` / `i386`）。
  与 `{{.Arch}}`（Go 的 `GOARCH`：`amd64` / `arm64`）并存不是冗余 —— release 资产命名
  两派都有：kubectl 用 `amd64`，docker compose 用 `x86_64`。
- 模板变量补齐 `{{.Filename}}` / `{{.Ext}}`，且 `ParseStr` 与 `ParseTargetPath`
  共用同一份上下文，两处不可能再漂移。
- `registry uninstall` 有了自己的 `-H/--hostname` 与 `-v/--version`（可选：
  卸载靠的是安装目录，既不看版本也不看主机名，给了值才校验格式）。
- `delete` 注册 `-n/--namespace`。
- `configs/tools.yaml` 改为三种 method 的可运行实战样例（kubectl / helm / jq）。

### Security

- **`images import` 不再信任归档里的条目名（CWE-22 / zip-slip）。**
  此前 `filepath.Join(tempDir, header.Name)` 直接采信外部输入：条目名写作
  `../../../etc/cron.d/x` 时 `..` 被规约掉，路径落到临时目录之外，随后攻击者提供的内容
  就被写进那个位置。离线镜像包正是设计上要在机器之间传递的东西，而 somcli 的典型运行
  身份是 root；写入还发生在 `docker load` **之前**，目标机上有没有 docker 都不影响利用。
  现在越界的条目名直接报错并中止，且只接受常规文件 —— 软链接一旦收下，
  后一个条目可以顺着它写到目录之外。
  *影响*：正常归档（`somcli images export` 产出的那种，条目名是扁平的 `.tar`）不受影响。
  *发现于* phase 1 收口评审，见 `review.md` R1。

### Fixed

- **`images export` 不再把半截归档报成成功。**
  真正把剩余压缩块刷进文件的是 `gzip.Writer.Close()`，而它此前是 `defer` 掉的、
  返回值被丢弃：磁盘满会得到一个能打开、解到一半报错的 `.tar.gz` 加一句"导出成功"。
  现在 `tar` → `gzip` → `file` 逐层 `Close` 并检查，任何失败都连带删掉产物 ——
  与"有失败就不写镜像清单"是同一条判据：半截产物比没有产物更危险。
  这同时关掉了本文件曾列为「已知欠账」的"失败时残留半截 `.tar.gz`"。
- `images import` / `export` 的临时目录从当前目录挪到 `<workdir>/tmp` 下并取独占名字。
  此前写作 `filepath.Join("temp-import")`，即相对**当前目录**：`--workdir` 被忽略、
  用户的工作目录里凭空多出一个 `temp-import`，两个并行的 somcli 还会互相覆盖中间产物。
- **`docker-compose install` 从"永远报告成功"改为真的安装。**
  此前复制到 `installPath`、`chmod 0755`、成功提示整段被注释掉，`installer.Install(...)`
  的返回值被丢弃，函数直接 `return nil`：404 也打印安装成功，而 `installPath` 上从没出现过任何东西。
  现在走 `method: binary` 这一条统一路径（下载、落盘、chmod、失败传播只有一处实现），
  装完还要校验：文件在、能执行、版本是入参那个 —— 否则就地报错，而不是等用户下次跑 compose 才发现。
- compose 安装不再忽略入参版本（`docker-compose install 2.30.0` 此前实际装 2.24.0），
  不再把架构硬编码成 `x86_64`（arm64 机器上必然 404），并删掉了非法模板 `{{}}`
  （`{{}}` 不是合法 Go 模板，解析必失败，而失败又被吞掉）。
- **`docker install -f nodes.yaml` 从必然失败改为可用。**
  `loadNodesFromFile` 此前函数体就是 `return nil, fmt.Errorf("... not implemented yet")`,
  docker 子系统的多节点能力 100% 不可用。现在复用与 install / cluster 相同的解析器
  （`UnmarshalStrict`，拼错的键直接报错），docker 子系统不再有自己的一套 `nodes:` 解析。
- **透传命令下 somcli 自己的全局 flag 生效且不泄漏给下游。**
  透传需要 `DisableFlagParsing`，而 cobra 在这个模式下既不解析根命令的全局 flag 也不摘掉它们：
  于是 `somcli --workdir /tmp/x docker-compose up` 的产物落回 `./somwork`（即仓库目录），
  同时 `--workdir /tmp/x` 被当作 compose 的参数传下去。
  现在先按"这个 flag 是不是 somcli 自己的"切分参数、解析、重新应用全局状态，剩下的才交给 compose。
  切分认不出的 token 一律倾向透传而不是吞掉 —— 下游自己的 `-p`（项目名）、`-e`（exec 环境变量）、
  `-f`（编排文件）此前被按名字硬摘，`compose -p myproj up` 丢了项目名。
- `--env-file` 原样转交给 compose。此前被写进 `COMPOSE_FILE` 环境变量 ——
  那是"编排文件"而不是"环境文件"，compose 会拿 `.env` 当 YAML 解析。
  文件不存在时明确报错，而不是静默忽略。
- `-d` 只补给 `up`。此前 `up` / `down` / `restart` 一律补，而后两者没有这个标志 ——
  `somcli docker-compose down` **必然**死在 `unknown shorthand flag: 'd'`。
  同时子命令识别从 `args[0]` 改为"第一个不是标志的 token"，`--env-file .env up` 这类写法才认得出。
- `extra_files` 真的落盘（渲染内容 / 建父目录 / 权限 0644）。此前 struct tag 写作
  `ExtraFiles`，与所有示例里的 `extra_files` 不匹配，字段永远是空的。
  远程分发走与下载产物完全相同的路径。
- 绝对路径 `target` 不再被无条件拼到缓存目录下；`target: bin/nested/tool.sh`
  这类带层级的路径会先建父目录（此前只建缓存目录本身，落盘直接失败）。
- 状态文件损坏时**降级为无状态执行**并出声警告，绝不因它而失败 ——
  它是本版本新增的产物，不能成为"装不上"的新原因。写入走临时文件 + rename，
  半截 JSON 会被判为损坏而丢掉整份账本，而不是被当成有效记录。
- 失败的资源/节点不记入状态（记了下次会被当成已安装跳过）。

### Changed

- 下载器改为只有 `net/http` 一条路径，不再 shell out 到 `wget`。
  0.2.0-alpha 的"已知欠账"里这条是留给本里程碑的：`http.DefaultTransport` 本身就走
  `ProxyFromEnvironment`，`HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY` 标准库直接认，
  所谓"wget/curl 用于走系统代理"的降级理由不成立。留着等于留一条永不触发、无人覆盖的分支。
  连带效果：不带 wget 的机器（含 macOS 默认环境）现在也能下载，相关场景不再跳过。
- 代理只对 github.com 生效，判据统一为主机名精确匹配或子域（`github.com.evil.com` 不再命中）。
  此前下载器用整条 URL 做 `Contains`、改写函数用主机名做 `Contains`，两道判据不一致，
  非 GitHub 地址会打出"用户使用代理"却并不真的走代理。
- 四种 method 安装器的签名由 `error` 改为 `([]string, error)`：方法本身不 exec，
  只把动作编译成命令列表交给 `utils.RunScripts`。于是"本机执行还是逐节点远程执行"
  只有一处实现，日志前缀、失败传播、`--parallel`、`on_error` 全部自动共享。
  直接后果：包管理器与容器运行时的探测写在**生成的 shell 里**（`if command -v apt-get …`），
  而不是 Go 侧的 `exec.LookPath` —— 判断必须发生在目标节点上。
- 模板渲染加 `Option("missingkey=error")`：上下文从结构体改成 map 之后，
  `text/template` 对缺键默认渲染 `<no value>` 而不报错，"引用未声明变量必须报错"
  这条判据会在实现变更后静默失效。
- integration 流水线的 multinode 作业名补齐为它实际承载的七个场景 ——
  作业名是别人判断"这条流水线守着什么"的唯一线索。

### 已知欠账

- `test/matrix.yaml` 的 28 个 `phase: 1` 场景中 5 条仍为 `pending`，缺的都是"另一半环境"：
  SC-M02（真实发行版上真装一次包，需多发行版容器矩阵）、SC-C01（真装一次 docker，
  需 docker-in-docker）、SC-C02（arm64 上不 404，CI 现在只跑 amd64）、
  SC-D10 / SC-F03（需一台真实远程主机）。
  声明了两个环境却只兑现一个就不置 `done` —— 否则 `done` 同时表示"全绿"和"绿了一半"。
- **somcli 该不该自己 `sudo`** 是未决的设计问题。`method: package` 生成的命令不带 sudo，
  非 root 直接失败；`install_dir` 缺省 `/usr/local/bin` 同样需要写权限
  （不想用 sudo 就 `--set bin=$HOME/bin`）。
- `images export` 失败时残留的半截 `.tar.gz` ~~不会被清理~~ → 收口评审时已修（见 Fixed）。
- 一台真正宕掉的节点会在文件分发阶段失败，此时即便写了 `on_error: continue` 整轮也会中止。
  要让"宕机节点自动被绕过"成立得先有节点可达性预检。
- `StrictHostKeyChecking=no`：首次连接不校验主机指纹，存在中间人风险。
