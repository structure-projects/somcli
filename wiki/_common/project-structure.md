# 项目结构约定

> 通用规则，适用范围：所有技术栈和项目类型。
> 各技术栈在其 `project-scaffolding.md` 中定义框架特定的模块模板和初始提交物。

## 目录组织原则

### 关注点分离

- **MUST** 按功能或领域划分目录，同一功能的代码聚合在一起。
- **MUST** 区分代码、资源（静态文件、模板）、配置和测试文件。
- **MUST** 通用代码和业务代码分离，通用代码可跨项目复用。

### 命名一致

- **MUST** 目录和文件名使用一致且描述性的命名，反映其用途和内容。
- **MUST** 目录名使用小写（kebab-case 或 snake_case，按语言约定）。
- **SHOULD** 目录名不使用复数（如 `model/` 而非 `models/`），除非语言约定要求。

### 嵌套深度

- **SHOULD** 目录嵌套不超过 4 层。
- **SHOULD** 当目录下文件超过 15 个时，考虑拆分子目录。

## 模块划分

### 目录类型识别（新建目录前 MUST 先判断）

用户说"新建目录 / 子目录"时存在歧义，**禁止默认按"子包"处理**——把特性目录建成 Java 子包会污染包结构且难以回退。

| 用户表达 | 目录类型 | 创建位置 | 影响包名 |
|---|---|---|---|
| "新建包 / 子包 / package" | **包目录** | 现有 package 下 | ✅ 影响（`package` 语句变化） |
| "新建特性 / feature / 业务模块" | **特性目录** | `features/<name>/` 或 `modules/<name>/` | ❌ 不影响（独立目录，跨层组织） |
| "新建文档 / 脚本 / 示例目录" | **非代码目录** | `docs/` `scripts/` `examples/` `assets/` | ❌ 不影响 |
| "新建子目录"（未明确） | **MUST 询问用户** | — | — |

三种目录的本质区别：

- **包目录**：Java package 的物理映射，影响 `package` 语句和 `import`
- **特性目录**：按业务特性跨层组织代码（如 `features/user-management/{controller,service,repository}/`），独立目录不影响主包结构
- **非代码目录**：不放源代码（如 `docs/design/`、`scripts/deploy/`）

识别困难时 MUST 按以下措辞询问用户：

> "您说的'子目录'是指：
> a) Java 子包（影响 package 语句）
> b) 特性目录（独立功能，跨层组织）
> c) 非代码目录（文档/脚本/资源）
> 请确认。"

禁止事项：

- ❌ **MUST NOT** 把"子目录"默认理解为"子包"
- ❌ **MUST NOT** 把"特性目录"创建为 Java 子包
- ❌ **MUST NOT** 在 `src/main/java/` 下创建非代码目录（如 `src/main/java/docs/`）

### 通用模块分类

| 模块类型 | 说明 | 包含内容 |
|---------|------|---------|
| **入口模块** | 应用入口、配置、启动 | 启动类、全局配置、生命周期管理 |
| **接口模块** | 对外暴露的 API | Controller/Handler、DTO/VO/Query |
| **业务模块** | 核心业务逻辑 | Service、DomainService、业务规则 |
| **领域模块** | 领域实体和仓储接口 | Entity、ValueObject、Repository 接口 |
| **基础设施模块** | 技术实现 | Repository 实现、DB 访问、缓存、消息、外部 API 客户端 |
| **公共模块** | 跨模块共享 | 工具类、常量、枚举、异常定义 |

### 通用目录结构

```
project-root/
├── {entry}/                  # 入口模块（boot/server/main）
│   ├── src/main/
│   ├── src/test/
│   └── config/
├── {api}/                    # 接口模块（interfaces/api/controllers）
├── {service}/                # 业务模块（application/service/biz）
├── {domain}/                 # 领域模块（domain/core/model）
├── {infra}/                  # 基础设施模块（infra/infrastructure）
├── {common}/                 # 公共模块（common/shared/base）
├── docs/                     # 设计文档（详见 documentation.md）
│   ├── overview.md           #   概要设计（项目定位+架构+技术栈+能力边界）
│   ├── features/             #   详细设计目录（每个功能一个 md）
│   ├── {version}/            #   版本快照（overview + features + changelog）
│   └── README.md             #   文档索引
├── scripts/                  # 构建/部署脚本
├── .github/workflows/        # CI/CD 流水线
├── README.md
└── CHANGELOG.md
```

## 配置文件

- **MUST** 配置文件按环境分离：
  - `application.yml`（或等效）：公共配置
  - `application-dev.yml`：开发环境
  - `application-test.yml`：测试环境
  - `application-prod.yml`：生产环境
- **MUST** 敏感配置（密码、密钥）通过环境变量或配置中心注入，**禁止**写在配置文件中。
- **SHOULD** 配置项使用清晰的命名，具有可读性。

## 资源文件

- **MUST** 资源文件（国际化、SQL 迁移、静态文件）与代码分目录存放。
- **MUST** 数据库迁移脚本按版本号命名（如 `V1.0__init_schema.sql`），放在 `resources/db/migration/` 或等效目录。
- **SHOULD** 国际化文件按语言代码命名（如 `messages_zh_CN.properties`、`messages_en_US.properties`）。

## 测试目录

```
{module}/
├── src/
│   ├── main/    # 源代码
│   └── test/    # 测试代码（镜像 main/ 结构）
│       ├── unit/          # 单元测试
│       └── integration/   # 集成测试
```

- **MUST** 测试目录镜像源代码目录结构。
- **MUST** 每个正式项目必须同时具备单元测试和集成测试。
- **禁止** 在正式项目中保留示例工程（`*-sample` / `*-example`）作为"测试替代品"。

## 文档目录

> 详细规范见 [`documentation.md`](documentation.md)。项目 MUST 在 `docs/` 下维护概要设计、详细设计、版本快照和变更日志。

## 依赖管理

- **MUST** 所有模块的依赖版本在父级或 BOM（Bill of Materials）中统一管理。
- **MUST** 子模块**不写死**依赖版本号。
- **禁止** 同一个依赖在不同模块中声明不同版本。

## 脚本目录

每个正式项目 **SHOULD** 提供以下脚本（位于 `scripts/` 目录）：

| 脚本 | 用途 |
|------|------|
| `build.sh` | 本地构建 |
| `test.sh` | 运行测试 |
| `run.sh` / `start.sh` | 本地启动 |
| `docker-build.sh` | 构建 Docker 镜像 |

- **MUST** 脚本首行 `#!/bin/bash`（或其他 shell），可执行（`chmod +x`）。
- **禁止** 脚本中硬编码密码/密钥 —— 凭据走环境变量。

## Dockerfile 规范

- **MUST** Dockerfile 位于入口模块目录（可运行的模块）。
- **MUST** 提供健康检查端点（`/health` 或 `/actuator/health`）供 K8s liveness/readiness probe 使用。
- **SHOULD** 使用多阶段构建减小镜像体积。
- **SHOULD** 提供 `.dockerignore` 排除无关文件。

## 父子项目约定

> 适用于使用父子嵌套 Git 项目（submodule / subtree / monorepo）的多项目生态。
> 核心原则：**有子项目的层负责概括，无子模块的叶子层负责完整细节**。规则在任意深度递归适用，实际项目中通常不超过 3 层。

### 多层嵌套模型

```
parent/                          # 根父项目（整体规划）
├── subsystem-a/                 # 中间层子系统（有子模块）
│   ├── module-a1/               #   叶子模块（无子模块，代码+完整文档）
│   └── module-a2/               #   叶子模块（无子模块，代码+完整文档）
└── subsystem-b/                 # 中间层子系统（有子模块）
    └── module-b1/               #   叶子模块（无子模块，代码+完整文档）
```

### 层级职责分离（递归模型）

> 规则在任意深度递归适用，实际项目中通常不超过 3 层。

| 层级 | 判断标准 | 职责 | 包含内容 | 禁止 |
|------|----------|------|---------|------|
| **根父项目** | 项目根，整合所有子系统 | 全局集成关系描述 | 全局架构图、模块清单、子系统间集成关系、全局规范 | 任何子系统的详细设计和 changelog |
| **中间层**（N 层） | 有子模块，但不是根 | 本级概要设计 | 本级功能架构、本级内模块关系、技术栈、依赖服务 | 详细设计、changelog、代码实现 |
| **叶子模块** | 无子模块，代码实际存放处 | 完整实现+文档 | 概要设计（父级上下文）+ 详细设计 + changelog + 版本快照 + 代码 + CI/CD | — |

### 根父项目职责（MUST）

- **MUST** 维护全局架构图：展示各子系统之间的集成关系和数据流向。
- **MUST** 维护模块清单：记录每个子系统和叶子模块的仓库地址、功能定位、负责人。
- **MUST** 定义全局规范：命名约定、技术栈基线、跨项目协作规则。
- **MUST** 描述集成关系：子系统间的 API 契约、消息通道、数据共享方式。
- **SHOULD** 在规划文档中只写概括，不深入到某个模块的实现细节。

### 中间层职责（MUST） — 递归适用

> 任何有子模块的非根层级均适用此规则，无论嵌套多深。

- **MUST** 维护本级概要设计（`docs/overview.md`）：本级的功能架构、技术栈、依赖服务、能力边界。
- **MUST** 描述本级内各子模块的职责划分和交互关系。
- **MUST** 概要设计需引用父级的架构设计，说明本级在父级中的位置。
- **禁止** 包含详细设计（`features/`）或变更日志（`changelog/`），这些由叶子模块维护。

### 叶子模块职责（MUST）

- **MUST** 维护概要设计（`docs/overview.md`）：聚焦本模块所在子系统的上下文和本模块的功能架构。
- **MUST** 维护详细设计（`docs/features/`）：每个功能的接口设计、业务流程、数据模型。
- **MUST** 维护变更日志（`docs/{version}/changelog/`）：记录每次代码变更的原始设计、变更内容和测试结果。
- **MUST** 维护版本快照（`docs/{version}/`）：版本发布时的完整设计状态。
- **MUST** 包含所有代码实现、单元测试、集成测试。
- **MUST** 包含 CI/CD 流水线文件、Dockerfile、部署配置等发布相关文件。

### 文档归属规则

| 文档类型 | 根父项目 | 中间层（N 层） | 叶子模块 |
|----------|:-------:|:---------:|:-------:|
| 全局架构图 | ✅ | — | — |
| 本级概要设计 | — | ✅ | ✅（父级上下文） |
| 模块清单 | ✅ | ✅ | — |
| 详细设计（features/） | — | — | ✅ |
| 变更日志（changelog/） | — | — | ✅ |
| 版本快照 | — | — | ✅ |
| 全局规范 | ✅ | — | — |
| CI/CD 流水线 | — | — | ✅ |
| Dockerfile | — | — | ✅ |

### 禁止事项

- **禁止** 根父项目或任意中间层维护详细设计文档。
- **禁止** 根父项目或任意中间层维护变更日志（changelog）。
- **禁止** 叶子模块定义父级或全局的架构。
- **禁止** 将 CI/CD 流水线、Dockerfile 等发布文件放在非叶子层级。
- **禁止** 叶子模块之间互相维护 changelog（各叶子模块独立管理）。
- **禁止** 在非叶子层级编写或修改代码实现（无论嵌套多深）。

## 禁止事项

- **禁止** 项目根目录散落过多配置文件（超过 5 个）。
- **禁止** 在正式项目中保留示例工程（`*-sample` / `*-example`）。
- **禁止** 测试目录和源码目录混在一起。
- **禁止** 密码/密钥/Token 硬编码在配置文件或脚本中。
