# 分层架构通用原则

> 通用规则，适用范围：所有技术栈和项目类型。
> 各技术栈在其 `architect.md` 中定义框架特定的分层实现和模块布局。

## 设计原则（SOLID + 补充）

- **MUST** **SRP（单一职责原则）**：一个模块/类只负责一件事，只有一个引起它变化的原因。
- **MUST** **OCP（开闭原则）**：对扩展开放，对修改关闭。新增功能通过扩展而非修改已有代码实现。
- **MUST** **LSP（里氏替换原则）**：子类可以替换父类而不破坏程序正确性。
- **MUST** **ISP（接口隔离原则）**：不应强迫客户端依赖它不使用的方法。大接口应拆分为多个小接口。
- **MUST** **DIP（依赖倒置原则）**：高层模块不应依赖低层模块，两者都应依赖抽象。抽象不应依赖细节，细节应依赖抽象。
- **SHOULD** **DRY（不要重复自己）**：提取共用逻辑到单独的函数/类/模块。
- **SHOULD** **KISS（保持简单）**：优先选择简单方案，不过度设计。
- **SHOULD** **YAGNI（你不会需要它）**：只在确实需要时才添加功能，不为"可能用到"而提前设计。

## 分层架构

### 通用分层模型

```
┌──────────────────────────────┐
│   接口层 (interfaces/api)     │  ← HTTP、RPC、消息消费入口
│   负责协议适配、参数校验      │
├──────────────────────────────┤
│   应用层 (application)        │  ← 用例编排、事务边界、权限校验
│   协调领域对象完成业务用例    │
├──────────────────────────────┤
│   领域层 (domain)             │  ← 核心业务逻辑、领域实体、领域服务
│   不依赖任何外部框架          │
├──────────────────────────────┤
│   基础设施层 (infra)          │  ← 数据库、缓存、消息、文件存储
│   实现领域层定义的接口         │
└──────────────────────────────┘
```

### 依赖方向

- **MUST** 依赖方向**只能自上而下**：接口层 → 应用层 → 领域层 → 基础设施层。
- **禁止** 反向依赖：领域层依赖基础设施层、应用层依赖接口层。
- **禁止** 跨层跳跃依赖：接口层直接依赖基础设施层。
- **SHOULD** 领域层通过接口（抽象）依赖基础设施，实现依赖倒置。

### 各层职责

| 层 | 职责 | 不负责 |
|------|------|--------|
| **接口层** | 协议适配（HTTP/gRPC/MQ）、参数校验、响应格式化 | 业务逻辑、数据库操作 |
| **应用层** | 用例编排、事务边界、权限校验、事件发布 | 领域规则、SQL/HQL |
| **领域层** | 业务规则、领域实体行为、状态机、值对象 | 持久化、序列化、网络通信 |
| **基础设施层** | 数据库访问、缓存、消息收发、文件存储 | 业务规则、流程编排 |

## 模块化

- **MUST** 按功能或领域划分模块，遵循"关注点分离"原则。
- **MUST** 模块间通过接口（抽象）通信，禁止直接依赖实现类。
- **MUST** 相关功能放在同一模块，减少跨模块依赖。
- **SHOULD** 模块命名反映其业务领域，而非技术细节。
- **SHOULD** 避免循环依赖 —— 出现时考虑提取公共模块或使用事件驱动解耦。

## 项目结构

- **MUST** 使用语言/框架的标准项目结构约定。
- **MUST** 区分代码、资源、配置和测试文件。
- **MUST** 集中管理依赖版本，禁止多处声明。
- **SHOULD** 目录嵌套不超过 4 层。

详见 [`project-structure.md`](project-structure.md)。

## 数据流

- **MUST** 数据在不同层之间传输时使用不同的数据结构（DTO / Entity / VO / PO），**禁止**数据库对象直达接口层。
- **MUST** 跨层转换在 Assembler / Mapper / Converter 中完成，不在业务逻辑中混入转换代码。
- **SHOULD** 读写分离：读模型可简化，写模型保持完整性（CQRS 原则）。

## 技术选型

- **MUST** 优先使用成熟的开源库和工具，避免不必要的自定义实现。
- **MUST** 利用语言/框架生态，不重新发明轮子。
- **MUST** 引入新的第三方依赖需要评估：活跃度（Star/维护频率）、License 兼容性、体积/性能影响。
- **禁止** 引入功能重复的依赖（如同时使用两个 JSON 库做业务序列化）。

## 输出要求（架构设计文档）

- **MUST** 包含：选型结论 + 模块划分图 + 依赖方向说明。
- **MUST** 设计偏离本文件时**显式说明冲突点与替代方案**。
- **SHOULD** 提供关键接口的契约定义（API 签名、事件格式、数据库 Schema）。

## 禁止事项

- **禁止** 循环依赖（模块间、类间）。
- **禁止** 领域层依赖框架特定注解/类（Spring、Django ORM 等）。
- **禁止** 接口层包含业务逻辑。
- **禁止** 跨层直接使用数据对象（如 Controller 直接操作 PO）。
- **禁止** 为了"更灵活"而过度抽象（一个接口只有一个实现类且永远不会有两个）。
