# 文档管理规范

> 通用规则，适用范围：所有技术栈和项目类型。
> 文档是设计的唯一事实来源，代码必须与文档保持一致。

## 设计目的

`docs/` 目录承载项目的全部设计资产，是**代码实现的依据**和**版本演进的记录**。任何代码变更前必须先有对应的设计文档，变更后必须更新文档并与代码保持一致。

## 目录结构

```
docs/
├── overview.md                    # 概要设计（项目级，长期维护）
├── features/                      # 详细设计目录
│   ├── feature-01-{name}.md       # 功能1详细设计
│   ├── feature-02-{name}.md       # 功能2详细设计
│   └── ...
├── {version}/                     # 版本快照目录（每个发布版本一个）
│   ├── overview.md                # 该版本的概要设计快照
│   ├── features/                  # 该版本的详细设计快照
│   │   ├── feature-01-{name}.md
│   │   └── ...
│   └── changelog/                 # 版本变更日志
│       ├── 001.md                 # 第1次变更记录
│       ├── 002.md                 # 第2次变更记录
│       └── ...
└── README.md                      # 文档索引（说明各文件关系）
```

## 一、概要设计（`docs/overview.md`）

### 必须包含的内容（MUST）

| 章节 | 说明 |
|------|------|
| **项目定位** | 系统解决什么问题，服务哪些用户 |
| **功能架构** | 系统功能模块划分图，各模块职责与边界 |
| **集成架构** | 与外部系统的集成关系图（依赖服务、中间件、第三方API） |
| **技术栈** | 语言、框架、数据库、缓存、消息队列等版本信息 |
| **依赖服务与组件** | 依赖的内部服务、组件库、基础设施清单 |
| **系统能力边界** | 明确系统做什么、不做什么（防止范围蔓延） |
| **核心设计示例** | 关键业务流程的概要描述（可引用详细设计文档） |
| **文档关系** | 引用 `features/` 下各详细设计文件，建立绑定关系 |

### 约束

- **MUST** 概要设计引用详细设计文档，建立明确的文档绑定关系。
- **MUST** 新增功能时，先更新概要设计（如功能架构图），再创建详细设计。
- **MUST** 架构变更时（X 版本递增），概要设计须同步重审并更新。

## 二、详细设计（`docs/features/`）

### 每个功能文档必须包含（MUST）

| 章节 | 说明 |
|------|------|
| **功能概述** | 功能目的、使用场景、用户角色 |
| **接口设计** | API 路径、请求/响应结构、错误码 |
| **业务流程** | 核心业务流程图或时序图 |
| **关键设计点** | 技术难点、设计决策、取舍理由 |
| **数据模型** | 涉及的表结构、实体关系（如有） |
| **页面交互**（前端） | 页面布局、交互流程、调用后端接口说明 |

### 命名规范

- **MUST** 文件名：`feature-{序号}-{功能名}.md`
  - 示例：`feature-01-user-login.md`、`feature-02-role-management.md`
- **MUST** 序号从 01 开始，不跳号。

### 约束

- **MUST** 新功能开发前，对应的详细设计文档必须已存在。
- **MUST** 功能变更时，同步更新对应的详细设计文档。
- **SHOULD** 详细设计文档中引用概要设计的章节编号，保持文档关联。

## 三、版本快照（`docs/{version}/`）

### 快照机制

- **MUST** 每次版本发布时，将当前 `docs/overview.md` 和 `docs/features/` 的完整内容复制到 `docs/{version}/` 目录。
- 快照记录了该版本发布时系统的完整设计状态。
- 禁止事后修改已发布版本的快照（它们是历史记录）。

### 约束

- **MUST** 快照在版本发布（打 tag）前完成。
- **MUST** 快照与代码版本一一对应，版本号与分支/代码一致。
- **禁止** 用快照替代 `docs/overview.md` 和 `docs/features/` 的日常维护（快照是只读历史，概要/详细设计是活的）。

## 四、变更日志（`docs/{version}/changelog/`）

### 日志文件格式

每个变更记录为一个独立的 markdown 文件，按序号命名：`001.md`、`002.md`...

```
docs/
└── 1.2.0/
    └── changelog/
        ├── 001.md    # 第一个功能：用户登录
        ├── 002.md    # 第二个功能：角色管理
        └── 003.md    # Bug 修复：登录超时
```

### 每条日志必须包含（MUST）

```markdown
# 变更 #{序号}：{变更标题}

- **类型**：feat / fix / refactor / docs / chore
- **日期**：YYYY-MM-DD
- **修改人**：{姓名或账号}

## 涉及文件

- `src/main/java/cn/structured/{module}/...` — 修改说明
- `docs/features/feature-01-xxx.md` — 设计文档同步更新

## 原始设计

> 变更前的设计描述（如为新增功能，标注"新增功能，无原始设计"）。

## 变更内容

> 本次修改的具体内容、设计思路、技术方案选择。

## 测试结果

- **单元测试**：通过 / 未通过
- **集成测试**：通过 / 未通过
- **影响范围**：{影响的模块/功能/接口列表}
```

### 约束

- **MUST** 每次提交代码时同步写入对应的 changelog 文件（序号递增）。
- **MUST** 每个功能或 Bug 修复对应一个独立的 changelog 文件，不合并。
- **MUST** changelog 序号与 PR 一一对应。
- **MUST** 测试结果必须如实填写，不可伪造。

## 五、AI 开发前置验证（MUST — AI 开发流程硬约束）

> 这是 AI 在编写任何代码前必须执行的验证步骤，确保"先设计、后编码"。

### AI 开发前检查清单

在执行任何代码变更前，AI **MUST** 按以下顺序完成验证：

1. **确认目标版本号**
   - 阅读 `docs/` 中的当前版本信息，确认本次变更的目标版本号。
   - 按 [`version-management.md`](version-management.md) 规则确定 X/Y/Z 哪段自增。
   - **禁止**在版本号不明确的情况下开始编码。

2. **验证设计文档存在**
   - 如果是**新功能**：检查 `docs/features/feature-{序号}-{功能名}.md` 是否已存在。
   - 如果是**Bug 修复**：检查 `docs/overview.md` 和对应功能的详细设计文档是否存在。
   - 如果设计文档不存在： **MUST** 先创建设计文档，再开始编码。

3. **确认预期交付**
   - 阅读设计文档，提取本次变更的预期交付物清单。
   - 向用户确认交付范围（如涉及多个功能/Bug，逐一确认优先级）。
   - **禁止**在预期交付不明确的情况下开始编码。

4. **变更中同步文档**
   - 编码过程中，每完成一个独立变更单元，同步更新 `docs/{version}/changelog/{序号}.md`。
   - 功能变更时同步更新 `docs/features/` 下的详细设计文档。

5. **交付前终验**
   - 确认代码变更与设计文档一致。
   - 确认 `docs/{version}/changelog/` 记录完整。
   - 确认 `README.md` 与当前版本代码一致（技术栈/配置/快速开始/模块说明等）。
   - 确认测试结果已填入 changelog。

### 禁止事项（AI 开发红线）

- **禁止** 在设计文档不存在的情况下编写功能代码。
- **禁止** 在目标版本号不明确的情况下开始编码。
- **禁止** 代码变更后不更新 changelog。
- **禁止** 跳过「确认预期交付」步骤直接编码。
- **禁止** changelog 中填写虚假的测试结果。
