# 迁移策略详解

> 本文档是 `project-intake` 技能的详细参考手册。

## 策略对比矩阵

| 维度 | 冻结 | 渐进改造 ⭐ | Strangler Fig | 整体重写 |
|---|---|---|---|---|
| **风险** | 低 | 低 | 中 | 高 |
| **工作量** | 最小 | 分散 | 大 | 最大 |
| **业务中断** | 无 | 无 | 无 | 有 |
| **技术债消除** | 不消除 | 渐进 | 逐步 | 一次性 |
| **团队要求** | 低 | 中 | 高 | 最高 |
| **推荐度** | 稳定老项目 | **推荐** | 大型重构 | 极少 |

## 冻结（Freeze）

### 适用

- 老项目进入维护期，不再演进
- 团队资源紧张，无重构时间

### 规则

- ❌ 老代码不动
- ✅ 新代码按新规范
- ✅ 新功能在新模块

### 风险

- 老代码永远是技术债
- 双规范长期并存可能混乱

## 渐进改造（Boy Scout Rule）⭐

### 原则

> "让代码比你来时更好一点"

每次 PR 顺手改造接触到的代码，不强制改造未接触的。

### 适用

- 持续维护的项目
- 团队接受渐进改进

### 规则

- ✅ 每次 PR 顺手改造接触到的代码
- ✅ 新功能 MUST 按新规范
- ✅ 修改老代码时顺手改造
- ❌ 不强制改造未接触的老代码

### 改造优先级

| 优先级 | 内容 |
|---|---|
| P0 | 安全相关（SQL 注入 / 越权） |
| P1 | 高频修改的模块 |
| P2 | 公共组件 / 工具类 |
| P3 | 边缘模块 |

### 工作量评估

- **每周改造 1-2 个文件**：分散到日常工作
- **每季度回顾**：评估改造进度

## Strangler Fig（绞杀者模式）

### 原则

新功能在新模块，老功能逐步替换，最终老模块被"绞杀"。

### 适用

- 大型重构
- 服务拆分（单体 → 微服务）
- 技术栈变更

### 流程

```
第 1 步：识别"接缝"（Seam）
   - 找出可以切分的边界

第 2 步：在接缝处建立代理层
   - 新请求 → 新模块
   - 老请求 → 老模块

第 3 步：新功能在新模块实现

第 4 步：逐步把老功能迁移到新模块

第 5 步：老模块功能全部迁移完成后，删除老模块
```

### 示例：单体拆微服务

```
初始：所有请求 → 单体应用

第 1 步：引入网关
   所有请求 → 网关 → 单体应用

第 2 步：新功能在新微服务
   新功能请求 → 网关 → 新微服务
   老功能请求 → 网关 → 单体应用

第 3 步：逐步迁移老功能
   老功能逐个迁移到微服务

第 4 步：单体应用功能全部迁移完成，下线
```

### 风险

- 需要维护路由层（网关）
- 双系统并行期间数据一致性
- 工作量大

## 整体重写

### 适用

- 极小项目（< 1000 行）
- 技术栈完全变更（如 PHP → Java）

### 规则

- ❌ 极少推荐
- ✅ 仅小项目
- ✅ 必须完整测试

### 风险

- 业务中断
- 高风险
- 可能引入新 bug

## 如何选择

```
Q1: 项目是否还在演进？
    ├─ 否 → 冻结
    ↓ 是
Q2: 是否需要大型重构 / 服务拆分？
    ├─ 是 → Strangler Fig
    ↓ 否
Q3: 团队是否接受渐进改进？
    ├─ 是 → 渐进改造 ⭐
    └─ 否 → 冻结
```
