# 版本管理规范

> 通用规则，适用范围：所有技术栈和项目类型。
> 版本号遵循 3 段式语义化版本，每次变更必须对应明确的版本号。

## 版本号格式

```
X.Y.Z
│ │ │
│ │ └─ 修复版本（Z）：Bug 修复时自增
│ └─── 功能版本（Y）：新增功能时自增
└───── 架构版本（X）：架构级别调整时自增
```

## 各段自增规则（MUST）

### X — 架构版本

以下变更 **MUST** 递增 X（同时 Y、Z 归零）：
- 模块拆分或合并（如 DDD 分层调整、微服务拆分）
- 框架大版本升级（如 Spring Boot 3 → 4）
- 破坏性 API 变更（不向后兼容的接口修改）
- 数据模型重大重构（无法通过迁移脚本平滑升级）

### Y — 功能版本

以下变更 **MUST** 递增 Y（同时 Z 归零）：
- 新增业务功能模块
- 新增对外 API 接口
- 新增中间件集成（如新增 MQ、新增搜索引擎）
- 新增前端页面或组件

### Z — 修复版本

以下变更 **MUST** 递增 Z：
- Bug 修复
- 安全漏洞修复
- 性能优化（不改变功能行为）
- 文档修正
- 依赖版本补丁升级

## 版本号约束

- **MUST** 版本号严格递增，**禁止**重复使用已发布的版本号。
- **MUST** 版本号**禁止**回退。
- **MUST** 开发阶段使用 `X.Y.Z-SNAPSHOT`，正式发布时去掉 `-SNAPSHOT`。
- **MUST** 发布后将版本号升级为下一个 `-SNAPSHOT` 版本（如 `1.2.0` 发布后改为 `1.2.1-SNAPSHOT`）。
- **MUST** 每次开发前明确目标版本号，分支命名与版本号对应。

## 分支与版本对应关系

| 分支类型 | 命名示例 | 目标版本 | 版本自增 |
|----------|----------|----------|----------|
| 功能开发 | `feat-1.2.0` | `1.2.0` | Y 自增 |
| Bug 修复 | `fix-1.1.1` | `1.1.1` | Z 自增 |
| 生产热修复 | `fix-1.0.1` | `1.0.1` | Z 自增 |
| 架构升级 | `feat-2.0.0` | `2.0.0` | X 自增 |

## 多模块项目版本

- **MUST** 所有子模块统一使用同一版本号，不各自独立。
- **MUST** 版本号通过父 POM 的 `${revision}` 统一管理。
- **MUST** 任一子模块有变更，整体版本号按上述规则递增。

## 发布流程

1. 确认目标版本号（按上述规则确定 X/Y/Z 哪段自增）
2. 在 `develop` 分支完成开发和自测
3. 更新 `docs/{version}/changelog/` 变更日志
4. 检查 `README.md` 是否需要同步更新（技术栈/配置/快速开始/模块说明等）
5. 提交 PR，合并到 `develop`
5. 打 tag `v{version}`
6. 触发 CI/CD 发布
7. 将 `-SNAPSHOT` 版本号升为下一版

## 禁止事项

- **禁止** 跳过版本号发布（"偷偷改"）。
- **禁止** 不明确目标版本号就开始开发。
- **禁止** 一个版本号下混合功能开发和 Bug 修复（应各自独立分支、独立版本）。
- **禁止** 在未更新 `docs/{version}/changelog/` 的情况下打 tag 发布。
- **禁止** 在 `README.md` 过期（与当前版本代码不一致）的情况下发布版本。
