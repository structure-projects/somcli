## 1. 背景与目标

somcli 的设计初衷是**初始化运行环境，并对业务服务或工具进行编排与实施**。容器/集群安装（Docker、Swarm、Kubernetes）是这一目标的应用场景之一，不是产品本体。

产品本体是 `resources:` 这一层通用编排引擎。它的执行语义已经成形：

```
resources 数组顺序 = 执行顺序
每个资源 = 下载 → 按 hosts 分发 → pre_install → post_install
脚本经 SSH 在目标节点执行
```

`configs/config.yaml:108-135` 已经把正确的上层架构画出来了 —— 集群定义不实现安装逻辑，只声明它由哪些**命名资源**组成：

```yaml
cluster:
  - name: "my-k8s"
    k8sConfig:
      resources: [kubernetes]   # 集群 = 命名资源的组合
```

**本提案的目标**：让代码回到这个架构上，并建立能持续保证它的测试与文档体系。

三条主线：

| 主线 | 目标 | 事实基准 |
|---|---|---|
| A. 架构收敛 | 通用引擎补全 → 集群安装改为消费配置而非硬编码 → 三套 schema 归一 | §2 功能清单与矩阵（21 个叶子命令 / 26 个能力域）、§4 现状基线 |
| B. 测试体系 | 全场景、全功能覆盖，GitHub Actions 流水线化 | §3 场景清单（82 个场景）、§6.8 功能 × 场景覆盖矩阵 |
| C. 文档重建 | 覆盖全部场景与功能；命令参考自动生成，从根上消除文档漂移 | §2 + §3 逐条落到 §7.1 的文档结构 |

三节之间是同一份事实的三种投影：**§2 说"有哪些功能"，§3 说"这些功能会被怎么用"，§6.8 说"每种用法由哪个测试守住"**。
验收（§9）不看主观描述，只看 §6.8 的 82 行是否全部有对应用例且 CI 绿。

| 命令 | 位置参数 | 标志 | 状态 |
|---|---|---|---|
| `somcli docker-compose`（别名 `compose`、`dc`） | 透传 | `-e/--env-file`、`-y/--yes`、`--path` | ❌ |
| `somcli docker-compose install [version]` | 可选 version | **无** | 🕳 |
| `somcli docker-compose uninstall` | 无 | **无** | ✅ |
| `somcli docker-compose version` | 无 | **无** | ✅ |

这个子系统是**问题最集中**的一处，以下全部已实测：

1. 🕳 **`install` 从不安装**：`pkg/compose/compose_installer.go:65-107` 中复制到 `installPath`、`chmod 0755`、成功提示**整段被注释掉**，`installer.Install(...)` 返回值被忽略，函数直接 `return nil`。**永远报告成功**。
2. ❌ **`--help` 会触发真实安装动作**：根命令设了 `DisableFlagParsing: true`（`cmd/compose.go:53`），`--help` 被当作透传参数。实测 `somcli docker-compose --help` 不打印帮助，而是开始下载并尝试安装 compose。**查看帮助产生副作用**，这是安全性问题。
3. ❌ **资源名拼写错误**：`applicationName = "docker-comopose"`（`pkg/compose/compose_installer.go:37`，`comopose`）→ 缓存目录实测为 `somwork/download/docker-comopose/2.24.0/`。
4. ❌ **忽略入参版本**：`Install(version string)` 内部用的是 `Version: defaultVersion`（第 81 行），`docker-compose install 2.30.0` 实际装 2.24.0。
5. ❌ **架构硬编码**：URL 模板固定 `-x86_64`（第 36 行）。实测在 arm64 macOS 上请求 `docker-compose-darwin-x86_64`。
6. ❌ **模板语法非法**：`PreInstall`/`PostInstall` 为 `["chmod +x {{}}"]`（第 84-85 行），`{{}}` 不是合法 Go 模板，解析必失败——而 `RunScripts` 把该错误吞掉（D2）。
7. 文档 `doc/docker-compose.md` 中的 `--version/-v`、`--github-proxy/-p` 均未注册（`--proxy` 的注册行被注释，`cmd/compose.go:77`）。

### 2.3 配置中存在但类型里不存在的字段（静默忽略全表）

`yaml.v2` 默认忽略未知字段，因此下列配置**写了等于没写，且不报错**。这是最隐蔽的一类缺陷。

| 文件 | 键 | 后果 |
|---|---|---|
| `configs/config.yaml` | 顶层 `cluster:`（整个数组，第 108-137 行） | `ResourceConfig` 无 `cluster` 字段 → **全部集群定义被丢弃** |
| `configs/config.yaml` | 顶层 `images:` | 静默忽略 |
| `configs/config.yaml` | `nodes[].mirrors_source` | 静默忽略（按节点换源能力不存在） |
| `configs/config.yaml` | `k8sConfig.runtime` | 键名应为 `containerRuntime` → 运行时选择无效 |
| `configs/config.yaml` | `k8sConfig.resources` | 静默忽略（**这正是目标架构的关键字段**） |
| `configs/config.yaml` | `cluster[].master` / `[].worker` | 静默忽略（类型只有扁平 `nodes` + 单数 `role`） |
| `configs/tools.yaml` | `source_url`、`package`、顶层 `hosts:` | 静默忽略 → **该文件整体不产生任何效果** |
| `configs/kubernetes-cluster.yaml` | `version`、`kind`、`Apps`、`flows`、`depends_on`、`roles`、`extra_files`、`sources` | 全部静默忽略 → 该文件是纯设计草案 |
| `configs/kubernetes-cluster.yaml` | `nodes[].roles`（复数） | 类型是单数 `role` → 角色声明失效 |

> 修法在 Phase 0/4：改用 `yaml.UnmarshalStrict`，未知字段直接报错；并由 L2 契约测试锁死（§6.2）。

## 3. 场景清单

功能回答"能做什么"，场景回答"在什么条件下做"。测试完整性由 **功能 × 场景** 的组合裁剪而来，
因此必须先把场景枚举清楚，否则"覆盖所有场景"这句话无法验证。

### 3.1 场景维度

任何一次 somcli 执行都可以由下面 7 个正交维度定位。缺陷往往只在某个维度的非默认取值上暴露
——例如 D1 只在"远程 + `cluster create`"下暴露，F5 只在"操作机 = macOS"下暴露。

| 维度 | 取值 | 当前唯一被覆盖的取值 |
|---|---|---|
| A 执行位置 | 本机 / 单远程节点 / 多远程节点 / 混合 | 仅本机（所有示例 `hosts: 127.0.0.1`） |
| B 网络模式 | 在线直连 / `github_proxy` 代理 / `mirrors_source` 换源 / 完全离线 | 在线直连 |
| C 安装方式 `method` | `binary` / `package` / `container` / `source` / `script` / `manifest` | 无区分（字段零消费，六者行为相同） |
| D 生命周期 | 首次安装 / 重复执行（幂等） / 版本升级 / 卸载 / 状态查询 | 仅首次安装 |
| E 失败模式 | 下载失败 / checksum 不符 / 脚本非零 / SSH 不可达 / 主机未声明 / 部分节点失败 / 模板错误 | 无（错误被吞，见 D2） |
| F 平台 | 发行版 × 包管理器 × 架构 × 操作机 OS | CentOS / yum / amd64 / Linux |
| G 上层应用 | 通用编排 / k8s / swarm / docker / compose / registry / images | — |

> 维度 A、C、D、E 的非默认取值目前**全部无覆盖**。这与 §4 的缺陷分布高度重合——
> 缺陷不是随机分布的，而是精确落在没有任何场景触达的区域。

## 5. 架构收敛方案

### 5.1 目标形态

```
                   ┌─────────────────────────────┐
   configs/*.yaml  │   声明层（用户可改）          │
                   │   resources / nodes /        │
                   │   cluster.resources[名称引用] │
                   └──────────────┬──────────────┘
                                  │
                   ┌──────────────▼──────────────┐
                   │   通用编排引擎（唯一执行路径） │
                   │   pkg/installer              │
                   │   解析 → 规划 → 分发 → 执行   │
                   │   method 分发 / 幂等 / 回滚   │

    strategy:
      fail-fast: false

## 9. 验收标准

验收的第一原则：**不看描述，看 §6.8**。§6.8 是 82 个场景到测试用例的一对多映射，它的机器可读版本是 `test/matrix.yaml`，
由 `test/coverage_matrix_test.go` 校验"每个场景 ID 至少被一个测试函数名引用"。矩阵不全 → 元测试失败 → CI 红。

| # | 标准 |
|---|---|
| 0 | **§6.8 的 82 个场景全部有对应用例，`test/coverage_matrix_test.go` 通过，且全部用例在 CI 中绿**（总验收门） |
| 0a | §2.4 的 26 个能力域全部达到该阶段的目标态；未达成项必须在 `doc/00-功能清单与矩阵.md` 中如实标注，不得标为可用 |

| 1 | 全部 D/E/F/G 编号缺陷均有对应自动化回归用例，且在修复前能复现失败 |
| 2 | `gofmt -l` 输出为空；`go vet`、`golangci-lint` 干净 |
| 3 | `pkg/installer`/`pkg/utils`/`pkg/cluster` 覆盖率 ≥ 80%，整体 ≥ 65% |
