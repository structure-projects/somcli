# 资源编排

> 覆盖验收场景：SC-E03、SC-E04、SC-E05、SC-E07、SC-E10、SC-E11、SC-E12、SC-E13、SC-E14、SC-E15、SC-M01、SC-M02、SC-M03、SC-M04、SC-M05、SC-M06、SC-F01、SC-F03、SC-F04、SC-F05、SC-F06、SC-F07、SC-F08、SC-X06、SC-X08。

somcli 把"要装什么、装到哪些机器、怎么装"写在一份 YAML 里。一条命令读这份文件，
按顺序把每个资源下载、分发、在目标上执行。本文是配置字段与执行模型的权威参考；
命令与标志见自动生成的 [`11-命令参考.md`](11-命令参考.md)。

完整可运行的示例：

- [`configs/tools.yaml`](../configs/tools.yaml) —— `binary` / `container` / `package` 三种 method。
- [`configs/examples/remote-3node.yaml`](../configs/examples/remote-3node.yaml) —— 三节点远程编排。
- [`configs/kubernetes-cluster.yaml`](../configs/kubernetes-cluster.yaml) —— 用 `hosts` 点名装一套 k8s。

## 1. 配置结构

一份配置是一个 YAML 文档（**不支持** `---` 多文档），顶层由几段组成，各命令只取自己那一段：

| 顶层键 | 类型 | 谁消费 |
|---|---|---|
| `offline` / `debug` / `github_proxy` / `workdir` | 标量 | 全局设置，对应同名标志 |
| `vars` | map | 自定义模板变量，模板里 `{{.Vars.xxx}}` |
| `source` | map | 装系统包前的换源配置，见 [`03-环境初始化.md`](03-环境初始化.md) |
| `resources` | 列表 | `install` / `uninstall` / `download` / `validate` |
| `nodes` | 列表 | 远程编排的节点清单，被 `resources[].hosts` 引用 |
| `cluster` | 列表 | `cluster create/remove/...` |
| `images` | 列表 | `images` 命令 |

未识别的键会被严格解析拒绝（不会静默忽略）。跑之前先用 `somcli validate -f <file>` 校验：
它解析、渲染所有模板、检查引用完整性，但不下载、不执行、不写文件。

## 2. 资源字段（`resources[]`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | string | 必填，资源名；也是状态记录与 `-n` 选择的键 |
| `version` | string | 版本，模板里 `{{.Version}}` |
| `method` | string | 安装方式，缺省 `script`，见下文 |
| `urls` | string 列表 | 下载地址，支持模板；逐个下载并分发到目标 |
| `target` | string | 下载产物的相对路径（相对缓存目录），支持模板 |
| `checksum` | string | 可选，`sha256:...`，校验下载产物 |
| `image` | string | `method: container` 的镜像 |
| `package` | string | `method: package` 的包名，缺省取 `name` |
| `install_dir` | string | `binary`/`container` 的落地目录，缺省 `/usr/local/bin` |
| `build` | string 列表 | `method: source` 在源码目录里执行的构建命令 |
| `files` | string 列表 | `method: binary` 时归档内要安装的可执行文件 |
| `extra_files` | map | 目标路径 → 文件内容，都过模板，落盘到目标节点 |
| `hosts` | string 列表 | 点名落到哪些节点（host 或 IP）；不写则在操作机本地执行 |
| `pre_install` | string 列表 | method 实施前的脚本 |
| `post_install` | string 列表 | method 实施后的脚本 |
| `remove_scripts` | string 列表 | 卸载脚本，`uninstall` 逆序执行 |
| `check` | string | 幂等探针：在目标上退出 0 则跳过整个资源 |
| `on_error` | string | `abort`（默认）/ `continue` |

## 3. 节点字段（`nodes[]`）

| 字段 | 类型 | 说明 |
|---|---|---|
| `host` | string | 主机名，`hosts` 可按它点名 |
| `ip` | string | 节点 IP，`hosts` 也可按它点名；SSH 连这个地址 |
| `role` | string | 单数字符串（`master`/`worker`/`manager` 等），仅作标记 |
| `user` | string | SSH 用户，缺省 `root` |
| `sshKey` | string | SSH 私钥路径，支持 `~` |

`role` 是单数。早期草案里的复数 `roles: [...]` 从未实现，严格解析下会报错；
按角色批量选节点也未实现——用每个资源的 `hosts:` 显式点名。未实现的设计见
[`roadmap.md`](roadmap.md)。

### hosts 与 nodes 的对应

- `resources[].hosts` 里的每一项必须命中某个 `nodes[].host` 或 `nodes[].ip`，
  否则 `validate` 与 `install` 都报"无法解析主机"。
- 例外：`localhost` / `127.0.0.1` / `::1` 是显式本机字面量，不经 `nodes` 声明即代表操作机。
- 不写 `hosts` 的资源在操作机本地执行（状态记为 `(local)`）。
- `--parallel N` 让脚本在最多 N 个 `hosts` 上并发执行（按资源、仅 hosts）。

## 4. method 的六种语义

| method | 做什么 | 必要字段 |
|---|---|---|
| `script`（默认） | 不做额外动作，安装就是 `pre_install`/`post_install` 本身 | 脚本 |
| `binary` | 下载物是归档就解开，把可执行文件装到 `install_dir`（0755） | `urls` |
| `package` | 把包名交给目标机器的包管理器（apt/dnf/yum/zypper/apk/brew） | `package` 或 `name` |
| `container` | 拉镜像，在 `install_dir` 放一个同名包装脚本，之后直接敲命令 | `image`、`name` |
| `source` | 把源码归档解到 `{{.SrcDir}}`，在那里执行 `build:` | `urls`、`build` |
| `manifest` | 把每个 `urls`/`extra_files` 清单交给 `kubectl apply -f` | `urls` 或 `extra_files` |

- `method: package` 在目标上需要 root 权限。加 `--sudo` 会在包管理器命令前加 `sudo`；
  默认不加，生成的命令与历史完全一致。换源由顶层 `source:` 驱动，见
  [`03-环境初始化.md`](03-环境初始化.md)。
- `method: manifest` 的 `hosts` 应指向一台有 kubeconfig 的 master：apply 是对集群做的，
  写多台等于把同一份清单 apply 多遍。
- 认不出来的 `method` 直接报错，不会静默当成 `script`。

## 5. 执行顺序与生命周期

每个资源按下述顺序处理，分发与执行都在**目标节点**上：

```
下载 urls → 分发到 hosts → 渲染并落盘 extra_files → pre_install → method → post_install
```

- 资源按 `resources:` 列表顺序安装；`uninstall` 按**逆序**执行 `remove_scripts`，
  先装的后拆。
- 下载发生在操作机，再通过 SSH 拷到每个目标的同一条绝对路径；本机目标跳过分发。

## 6. 模板变量

脚本（`pre_install`/`post_install`/`remove_scripts`/`build`/`check`）、URL、`target`、
`extra_files` 的键值都过同一套模板。`target` 比脚本多绑定"当前 URL"推导出的 `Filename`/`Ext`，
但资源通常只有一个 URL，脚本里写 `{{.Filename}}` 也指向第一个 URL 的文件名。

| 变量 | 含义 |
|---|---|
| `{{.Name}}` | 资源名 |
| `{{.Version}}` | 资源版本 |
| `{{.Arch}}` | 目标架构（`amd64`/`arm64`） |
| `{{.UnameArch}}` | `uname -m` 风格（`x86_64`/`aarch64`） |
| `{{.Platform}}` | `linux`/`darwin` |
| `{{.Filename}}` | 从 URL 推导的文件名 |
| `{{.Ext}}` | 从 URL 推导的扩展名（含点） |
| `{{.CacheDir}}` | 本资源的缓存目录（`<workdir>/downloads/<name>/<version>`） |
| `{{.SrcDir}}` | `{{.CacheDir}}/src`，`method: source` 的解压目录 |
| `{{.InstallDir}}` | `install_dir`（缺省 `/usr/local/bin`） |
| `{{.WorkDir}}` | 工作目录 |
| `{{.DownloadDir}}` / `{{.ImagesDir}}` / `{{.ScriptDir}}` / `{{.TmpDir}}` | 工作目录下的固定子目录 |
| `{{.Vars.xxx}}` | `vars:` 定义的自定义变量 |

模板开了 `missingkey=error`：拼错变量名会当场报错，不会静默产出 `<no value>`。
集群清单（`configs/k8s/*.yaml`）另外有 `{{.Vars.k8sVersion}}` 等由 `cluster create`
注入的变量，那套变量只在集群编排时可见。

## 7. 幂等与失败策略

- **幂等探针**：资源写了 `check:`，somcli 在目标上执行它；退出 0 就认为已装，跳过整个资源
  （method 与 post_install 都不跑）。适合"装一次就够"的资源。
- **状态记录**：`<workdir>/state.json` 记录每个资源在每个目标上装过的版本。已记录且版本
  相同则跳过；改 `version:` 或加 `--force` 会重新执行。`somcli status` 可查看记录。
  （`base-dependencies`、`docker` 等少数资源每次都强制执行，不受状态跳过影响。）
- **失败策略**：`on_error: abort`（默认）在第一个资源失败时立即中止；`on_error: continue`
  跳过失败的目标与本资源、继续后续资源，但进程退出码仍非 0。

## 8. 离线与代理

- `--offline` 或顶层 `offline: true`：不发起任何下载，假设产物已在缓存目录。
- `--github-proxy` 或顶层 `github_proxy:`：给 GitHub 下载地址加前缀代理。
- 离线整体流程见 [`10-离线部署.md`](10-离线部署.md)。
